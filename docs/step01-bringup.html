KR260 Custom Accelerator — Toolchain Reference

Bringing Up Step 01

The Vivado side of step 01 was almost nothing. The real milestone was getting PYNQ to run on the board at all — twice.

The bitstream itself is a Zynq UltraScale+ PS with no programmable-logic content whatsoever — built purely to prove the toolchain could produce a .bit/.hwh pair PYNQ would accept. See vivado/step01_hello/build.tcl: one PS block, the KR260 board preset applied, and both general-purpose AXI master ports forced off, since with no custom IP to drive them their clock pins fail validation left on. No block-design GUI session was needed here — with just the PS and nothing to wire it to, the whole design is a handful of create_bd_cell/apply_bd_automation calls written directly into build.tcl.

Everything that actually took effort happened after the bitstream existed: getting PYNQ installed on hardware Xilinx doesn't officially image this way, and then getting overlay loading to work under sudo. Two separate debugging sagas, both resolved the same way — by finding whoever on the board had already solved the problem, rather than guessing.

Act 1 — Getting PYNQ to install at all

A plain pip install pynq assumes the headers, libraries, and CMA allocator that Xilinx's own board image pre-bundles. This KR260 runs stock Canonical Ubuntu, so none of that existed yet — three unrelated-looking failures in a row, each one peeling back another missing layer, all pointing at the same underlying mismatch.

The consequence that outlives the install itself: because PYNQ lives in its own venv rather than system Python, every script that touches it has to use /usr/local/share/pynq-venv/bin/python3 explicitly — a plain python3 or sudo python3 silently resolves to the wrong interpreter and won't find PYNQ at all.

Act 2 — Getting sudo to agree with PYNQ

Installed didn't mean working. Loading an overlay needs XRT talking to the device, which needs root — and two more failures showed up under sudo: pynq.Device reported no devices even though xbutil examine outside Python saw the board fine, and once that was patched by hand, Overlay() failed with a FileNotFoundError because the board has two copies of xclbinutil and the Ubuntu apt package's one segfaults. Hand-plumbing sudo VAR=… PATH=… lines fixed it but felt like guesswork — so instead of guessing further, the question became: what already works as root on this board?

Confirmed on the board:

$ ./run_pynq.sh load_overlay.py Overlay loaded successfully. IP cores in overlay: ['zynq_ultra_ps_e_0'] Step 01 PASS
