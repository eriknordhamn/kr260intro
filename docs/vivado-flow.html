KR260 Custom Accelerator — Toolchain Reference

The Vivado Flow

How a hand-written AXI4-Lite register becomes a bitstream running on the KR260 — and which two steps still need a human at the mouse.

Vivado's design flow runs almost entirely from the command line in this project — RTL, simulation, project creation, synthesis, and implementation are all plain Tcl, run in batch mode. Two moments are the exception: packaging custom RTL as an IP core, and wiring components together on the block-design canvas. Both lean on GUI-only tooling — interface auto-detection, Connection Automation — that has no scripted equivalent worth hand-writing.

The trick is that both are needed only once. Vivado can export exactly what happened in a GUI session as a Tcl script, so every rebuild after that — including the one that just finished — replays it headlessly. The diagram below traces the whole path for step 02, the AXI-Lite echo register.

Reading the pipeline

01

RTL & simulation

axi_lite_echo.sv is a hand-written, unpipelined AXI4-Lite slave — one 32-bit register, no address decode. tb_axi_lite_echo.sv exercises it directly under xsim, no Vivado project involved. This is the fast loop: seconds per run, against the ~20 minutes a full bitstream rebuild costs further down the chain.

02

Packaging custom IP GUI once

The block-design canvas only places IP-XACT components, not raw RTL. package_ip.tcl packages the module by inferring its AXI4-Lite, clock, and reset interfaces straight from the S_AXI_* signal names — no manual wiring. The one GUI session here existed only to confirm that inference looked right before trusting it headlessly; the script reproduces it exactly, every time, with no window ever opening.

03

Block design GUI once

axi_lite_echo_overlay_bd.tcl is Vivado's own File → Export Block Design as TCL output, committed close to verbatim. It recreates the Zynq PS (board preset, one AXI-Lite master port enabled and the rest off), the packaged IP, the SmartConnect and reset block that Connection Automation inserted, and the register's address assignment at 0xA0000000.

04

Build

build.tcl ties it together: create the project, register the IP repository, source the block-design script, wrap it for synthesis, then launch_runs synth_1 and impl_1 through to write_bitstream — checking PROGRESS after each and erroring out loudly rather than continuing on a bad run.

05

Deploy

The resulting .bit and .hwh copy to the board, where sw/run_pynq.sh — never a bare sudo python3 — runs the PYNQ driver that loads the overlay and exercises the register from Python.
